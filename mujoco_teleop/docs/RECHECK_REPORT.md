## 为什么当前不能按教程直接训练 π0

这是三个不同层次的问题，不能只归因于 Windows 或下载文件大。

**导入错误已修复。** π0 模型现在可以导入，也能在不分配大型张量的 meta 设备构造完整架构。但这还不代表已经读取了预训练权重或做了真实反向训练。

**实际访问仍被阻止。** π0 源码会调用 `AutoTokenizer.from_pretrained("google/paligemma-3b-pt-224")`。本次实际执行这个调用：当前进程未发现 Hugging Face 凭据，请求返回 HTTP 401。仅能查看 `lerobot/pi0` 的公开配置不等于有权下载 PaliGemma 分词器。需要具有该模型访问权限的账号与可用凭据；反复安装包无法解决授权。

**教程默认显存需求超过本机。** 用固定版的真实 π0 架构统计 3,501,372,176 个参数，保留其混合 BF16/FP32 类型，得到：

| 配置 | 参数权重 | 权重 + 梯度 + Adam 两份状态估算 |
| --- | --- | --- |
| 上游默认：冻结视觉、继续训练语言/动作部分 | 7.02GiB | 22.83GiB |
| 仅训练动作专家及投影层 | 7.02GiB | 8.80GiB |
| 本机 GPU 总容量 | **7.93GiB** | 操作系统/其他程序还会占用一部分 |

估算按参数当前类型计算梯度与 Adam 状态，已经排除未参与自定义 forward 的专家 `lm_head` 梯度/状态；未包含激活、CUDA 工作区、缓存及分配器开销。它是 **meta 参数估算，不是本机实测峰值，也不是故意触发的 OOM**。磁盘上的 checkpoint 字节数没有直接当作训练显存。

在当前教程的标准参数/AdamW 方案下，授权解决后仍有显存瓶颈。换 Ubuntu 或再建 VMware 虚拟机不会增加物理显存。量化、LoRA、优化器压缩、CPU 卸载等是其他方案，本次没有验证，不能据此声称 8GB 对所有可能方案都绝对不行。

## 为什么当前不能按教程直接训练 π0.5

**现有环境用途是数据测试。** `.venv-pi05` 实际为 Python 3.12.13、torch 2.7.1+cpu，`torch.version.cuda=None`、`cuda_available=False`。该环境没有安装完整 `lerobot[pi]` 模型 extras；真实模型构造首先报缺少 `transformers`。能导入类或通过六项接口测试，均不代表能构造并训练完整模型。

**上游完整安装文件在 Windows 存在确定冲突。** 用 `uv pip install --dry-run` 实际解析原 `requirements_pi05.txt`，未安装或升级任何包。解析器返回无解：

```text
requirements_pi05.txt: torchcodec==0.4.0
LeRobot 0.6.1 training -> dataset on win32: torchcodec>=0.7.0,<0.12.0
```

因此不能把这份原安装文件直接用于当前 Windows GPU 环境。当前 CPU 数据环境使用独立锁文件和嵌入图像/PyAV 路线，不依赖 TorchCodec，所以数据转换能运行。将来配置完整训练环境需要单独适配这些约束，不能靠向 my_env 混装两个版本解决。

**显存仍需另行满足。** 上游记录的一次 batch=1、只训练动作专家、BF16、梯度检查点的 π0.5 五步微调，峰值分配显存为 12.85GiB，已经超过本机 7.93GiB。这个数值来自上游工作站实验，**不是本机测出来的硬性下限**。当前没有在本机加载完整 π0.5 权重或实际训练，所以不把它写成“本机 OOM 已复现”。
